# Internationalization (i18n) — two models

This project mixes **two different i18n mechanisms**. Know which one a field uses
before you query it, preview it, or add a new translatable field — they behave
differently and are filtered differently in GROQ.

Locales: `fr`, `en`, `es` (default `en`). Defined in `sanity.config.ts`
(`SUPPORTED_LANGUAGES`) and `i18n/routing.ts`.

---

## Model A — Document-level (`@sanity/document-internationalization`)

**One document per language**, linked together by separate `translation.metadata`
documents.

- **Used by:** the types in `TRANSLATABLE_TYPES` (`sanity.config.ts`) →
  `page`, `board`, `accessory`.
- **Marker:** each document has a hidden, **required** `language` string field.
  The plugin writes it; don't set it by hand.
- **Creation:** only via the per-language templates (`board-en`, `accessory-fr`, …)
  surfaced in the language-grouped structure panes. The bare templates
  (`board`, `page`, `accessory`) are removed from every "+" button
  (`newDocumentOptions`) so a document can never be created without a language.
- **GROQ:** filter the documents themselves on the top-level `language` field:

  ```groq
  *[_type == "board" && language == $locale]
  ```

- **Translated slugs / linked translations:** resolve via `translation.metadata`:

  ```groq
  "translations": *[_type == "translation.metadata" && references(^._id)][0]
    .translations[]{ "lang": value->language, "slug": value->slug.current }
  ```

## Model B — Field-level (`sanity-plugin-internationalized-array`)

**One document**, but the translatable field is an **array of per-language values**.

- **Used by** (types `internationalizedArrayString` / `internationalizedArrayText`):
  e.g. `series.name`, `accessoryCategory.name`, the `boardsPageSettings` /
  `accessoriesPageSettings` SEO fields, and `page.heroSubtitle`.
  **Source of truth — for the exact current list:**

  ```bash
  grep -rn "internationalizedArray" sanity/schemas/
  ```
- **Shape of each array item:**

  ```json
  { "_key": "9c75c637…(random hash)", "_type": "internationalizedArrayStringValue",
    "language": "en", "value": "Tiki Series" }
  ```

### ⚠️ The gotcha: filter on `language`, NOT `_key`

In these arrays the locale code lives in **`.language`**. `_key` is a **random
hash** (NOT the locale). Filtering on `_key` silently returns nothing and falls
back to the first item — so you get the wrong language with no error.

```groq
// ✅ correct
"name": coalesce(name[language == $locale][0].value, name[language == "en"][0].value, name[0].value)

// ❌ wrong — _key is a hash, this always misses
name[_key == "en"][0].value
```

The same rule applies to **Studio `preview.prepare()`** functions that read these
arrays — use `.find(n => n.language === 'en')`, not `n._key`:

```ts
name?.find((n: { language: string; value: string }) => n.language === 'en')?.value
  ?? name?.[0]?.value
```

## Quick reference

| Concern                        | Model A (document)        | Model B (field array)            |
| ------------------------------ | ------------------------- | -------------------------------- |
| Plugin                         | document-internationalization | internationalized-array      |
| Granularity                    | whole document per locale | one field, array of locales      |
| Locale lives in                | top-level `language` field | each array item's `.language`   |
| GROQ filter                    | `language == $locale`     | `field[language == $locale]`     |
| `_key`                         | n/a                       | random hash — **never filter on it** |
| Examples                       | page, board, accessory    | series.name, *.seoTitle, heroSubtitle |

## Adding a new translatable thing

- **A whole new content type** that needs full translations (own slug, body, SEO)
  → Model A: add it to `TRANSLATABLE_TYPES` and give it the hidden required
  `language` field.
- **A short label on an otherwise single document** (a name, a tagline, an SEO
  string) → Model B: use `internationalizedArrayString` / `…Text`, and remember
  to query/preview it via `language`, not `_key`.
